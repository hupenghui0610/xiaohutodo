# 多端静默同步设计

## 背景与目标

当前 To-do List 在登录成功后只加载一次，文档链接在首次进入对应 Tab 时加载一次；加载成功后，两者都长期使用页面内存中的数据。网页端、PC 端或另一台电脑修改数据时，已打开的页面不会主动感知，只有重新加载页面才会得到最新状态。

本次改造目标是在不刷新整页、不清空现有内容、不显示整块 loading 的前提下，让多个客户端低成本地同步最新数据：页面保持前台时最长约 60 秒感知远端变化，从其他应用切回页面时立即检查，并且只更新实际发生变化的数据行。

## 用户体验

- 登录成功后同时启动待办和文档数据的后台预取，不再等待用户首次进入“文档链接”Tab 才开始请求。
- 页面持续处于前台时，每 60 秒执行一次轻量版本检查。
- 页面进入后台后暂停周期检查；重新回到前台或窗口重新获得焦点时立即检查一次。
- 同一次可见性变化和焦点恢复只合并为一次检查，避免连续重复请求。
- 版本没有变化时不请求完整列表，也不触碰页面 DOM。
- 版本发生变化时只拉取对应数据域，并按稳定 ID 新增、删除或更新具体行。
- 后台同步期间保留现有内容、滚动位置、焦点、Tab 状态和编辑器，不显示“正在加载”界面。
- 首次打开且本地尚无任何页面内数据时，内容在请求完成后直接填入；请求期间保持稳定的空容器，不显示误导性的“暂无数据”或 loading 文案。
- 后台同步失败时继续显示旧内容，不弹窗打断用户；下一次检查自动重试。只有用户主动保存失败时才沿用现有错误反馈。
- 不将待办或文档业务数据持久化到 `localStorage`、`sessionStorage` 或 IndexedDB，避免共享电脑上的数据残留。

## 同步架构

### 轻量版本接口

新增当前用户范围的同步状态接口 `GET /api/sync-status`，返回：

```json
{
  "code": "OK",
  "data": {
    "todosRevision": 12,
    "directoriesRevision": 4,
    "documentsRevision": 9
  }
}
```

新增 `user_data_revisions` 表，每个用户一行，分别保存待办、目录和文档的单调递增整数版本。不存在记录时按零处理并按需初始化。数据库迁移同时为三个业务表建立 INSERT、UPDATE、DELETE 触发器，由触发器在业务语句的同一事务中递增对应 revision。

- 待办新增、修改或删除成功时递增 `todos_revision`。
- 目录新增、改名、排序或删除成功时递增 `directories_revision`。
- 文档新增、修改或删除成功时递增 `documents_revision`。
- 业务写入触发 revision 递增，两者属于同一数据库语句事务，保证不会出现“数据已改变但版本未改变”或相反的状态。
- 文档变化导致的目录文档数量由客户端基于最新文档集合重新计算，因此不额外递增目录版本。
- 同步状态响应继续使用 `Cache-Control: no-store`，任何检查都不能从浏览器 HTTP 缓存取得旧版本号。

### 客户端同步协调器

新增单一同步协调器负责登录后启动、登出后停止、定时检查、可见性检查和并发合并。协调器本身不直接操作 DOM，只调用两个数据 store 的同步入口。

- 一个页面同时最多存在一个版本检查请求。
- 检查进行中收到新的触发时不并发发送请求；当前检查完成后仅在确有必要时补一次。
- 周期计时从上一次检查完成后开始，避免慢请求堆叠。
- `document.hidden === true` 时不发周期请求。
- `visibilitychange` 变为可见和 `window.focus` 共用短时间去重，恢复页面时最多触发一次检查。
- 登录用户变化或退出登录时停止计时器、废弃在途结果并清空页面内版本状态，防止跨账号串数据。

### 首次加载与后续同步

登录成功后并行加载待办、目录和文档。三个列表 GET 接口都在同一个 D1 batch 中读取业务列表和对应 revision，并在响应中返回该 revision；首次成功结果既建立页面数据，也建立与该列表一致的版本基线。不得先读列表、再用独立请求读取版本作为该列表的基线，以免漏掉两次读取之间发生的远端修改。

后续检查比较服务端版本与本地基线：

- `todosRevision` 变化时请求最新待办列表。
- `directoriesRevision` 变化时请求最新目录列表。
- `documentsRevision` 变化时请求最新文档列表。
- 多个版本同时变化时并行请求对应列表，全部结果按数据域独立应用；某一域失败不阻止其他域更新。列表响应携带的 revision 必须与返回数据来自同一 D1 batch 快照。
- 只有完整列表请求成功并应用后，才推进该数据域的本地版本基线。失败的域保留旧基线，以便下次继续重试。

## 差量页面更新

### To-do List

待办节点以待办 ID 为键进行协调，不再在后台同步时清空 `listA`、`listB` 或日待办容器。

- 新 ID：在正确分组和排序位置插入节点。
- 已删除 ID：只删除对应节点。
- 已存在且字段变化：只更新标题、完成状态、延迟标记、日期、周归属等受影响内容；需要跨分组时移动原节点或重建该单行节点。
- 未变化 ID：保留原 DOM 节点，不重设内容。
- 数量、空状态和日期分组统计只更新受影响的文本。

现有全量 `renderAll()` 仍可用于首次渲染和用户切换查看周；后台同步必须走独立的 keyed reconciliation 路径。

### 文档链接

目录和文档节点分别以目录 ID、文档 ID 为键协调。

- 目录新增、删除、改名或排序时只操作对应目录容器及顺序。
- 文档新增、删除、修改或移动目录时只操作对应文档行。
- 目录文档数量根据最新文档集合重算，仅更新数量文本。
- 未变化的目录和文档节点保持不动。
- 后台同步不得通过 `replaceChildren` 重建整个文档区域。

## 编辑与冲突处理

后台同步不得覆盖用户尚未保存的输入。

- 用户正在编辑的待办或文档行标记为本地受保护项。
- 远端同一条记录发生变化时，先保存远端版本信息，但保持当前输入框、光标和草稿不变。
- 待办表新增 `updatedAt` 字段；文档继续使用现有 `updatedAt`。编辑开始时记录基础版本。
- 保存时把基础 `updatedAt` 一同提交。服务端仅在记录当前版本仍等于基础版本时更新，否则返回 `409 EDIT_CONFLICT`，并附带当前远端记录。
- 发生冲突时保留本地草稿，显示行内提示：“该内容已在其他设备更新”。用户可以选择“使用远端内容”或“仍然覆盖”。
- “使用远端内容”放弃本地草稿并应用服务端记录；“仍然覆盖”使用显式覆盖参数再次提交，并以新的版本写入。
- 远端已删除而本地仍在编辑时使用同一冲突界面说明“该内容已在其他设备删除”，允许放弃本地草稿；不自动重新创建。
- 不处于编辑状态的同一记录采用服务端最新状态。

目录重命名不引入长期草稿，若保存时版本冲突则保留输入并显示同类行内提示；目录排序和删除继续以服务端结果为准。

## 写入后的本地一致性

- 当前客户端写入成功后立即应用接口返回的记录和新版本，不等待下一轮轮询。
- 服务端写接口使用一个 D1 batch 执行业务写入、读取写入后的记录和读取对应 revision，响应返回结果记录及 revision。客户端只有在响应数据足以反映该 revision 对应状态时才直接推进基线；若响应 revision 高于本次写入预期，立即安排一次该数据域静默同步，避免跳过并发写入。
- 待办差异快照必须在后台同步后更新为服务端最新集合，避免把远端新增误判为本地删除，或把远端修改误判为本地写入。
- 写入和后台同步同时发生时，以请求开始时的 generation 和记录版本判断结果是否仍可应用；旧请求不得覆盖更新结果。

## 性能与流量

- 正常前台页面每分钟只有一次轻量版本请求；后台页面不轮询。
- 只有发现版本变化时才下载完整数据域。
- 页面恢复焦点时的检查与 60 秒周期检查合并，避免双请求。
- 多个页面的周期起点加入少量随机抖动，避免大量客户端整分钟同时请求。
- 不引入 WebSocket、SSE 或第三方实时同步依赖。

## 异常处理

- 版本检查失败：静默保留旧内容，下一个周期重试。
- 某数据域刷新失败：其他成功数据域正常更新，失败域下次重试。
- 身份失效：沿用现有 `auth-required` 流程，不继续后台请求。
- 页面离线：不弹重复错误；恢复网络并重新获得焦点或到达下一周期后重试。
- 返回数据格式无效：拒绝应用该数据域结果，保留当前页面状态和本地 revision。

## 测试与验收标准

自动化测试至少覆盖：

1. 登录后并行预取待办、目录和文档，首次进入文档 Tab 不再触发 loading 界面。
2. 页面可见时按 60 秒检查版本，隐藏时停止，恢复可见或获得焦点时立即检查且事件去重。
3. 版本未变化时不请求完整列表，也不调用 UI 更新。
4. 单个数据域版本变化时只请求对应列表；多个变化域可并行同步。
5. 后台同步不清空容器，未变化记录保持同一个 DOM 节点实例。
6. 新增、删除、修改和跨分组移动只影响对应待办或文档节点。
7. 同步前后滚动位置、活动 Tab 和未涉及的输入焦点保持不变。
8. 正在编辑的记录收到远端变化时保持本地草稿，不替换输入 DOM。
9. 版本冲突返回 409 后可选择使用远端版本或显式覆盖。
10. 同步失败保留旧数据并在后续周期重试，不显示 loading 或阻断弹窗。
11. 登录用户变化后废弃旧账号的在途同步结果。
12. 每个业务写入与 revision 递增保持原子性，列表数据与其 revision 来自同一 D1 batch 快照。
13. 待办同步更新差异快照，不会误删或覆盖另一设备新增的待办。

人工验收包括：

- PC 端保持前台，网页端修改后，PC 端在 60 秒内只改变对应行，无整页闪烁。
- PC 端切到其他应用，网页端修改后，切回 PC 端立即静默更新。
- 首次进入文档链接 Tab 不出现“正在加载…”占位。
- 编辑输入过程中远端同步不造成失焦、光标跳动或草稿丢失。
- 断网、弱网和服务端暂时失败时旧内容保持可用，界面不反复提示。

## 非目标

- 不实现秒级实时协作、共同光标或逐字同步。
- 不通过 WebSocket 或 SSE 推送变化。
- 不持久化业务列表到浏览器本地存储。
- 不改变现有两个一级 Tab 的视觉设计和导航结构。
- 不自动合并两端对同一文本字段的不同编辑内容。
